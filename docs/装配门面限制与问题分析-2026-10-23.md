# 装配门面（bootstrap 门面）限制与问题分析

> 分析时间：2026-10-23 00:50 (UTC+8) · 对象：雪豹决策核心
> 由来：`开发者理解成本分析-2026-10-23.md` §六.1 的待裁决项——是否加 `SnowLeopard.bootstrap(root)` 式装配门面。
> 本文只分析**限制与问题**并给出约束条件与对照方案；结论供裁决，不含改动。

---

## 〇、门面想解决什么（回指）

现状：宿主必须自己按序拼装 `Ids.at(root) → ToolRegistry → ProviderLoader → Permissions → 各 Store`，
装配顺序与依赖约束（`Permissions.defaultAll` 需先有 registry；`Rollup` 需先有 RawLog+MemoryStore+Compressor）
**只隐含在 9 个 Check 的 setup 里**，属默会知识。门面把这条装配链固化为一个入口，消灭顺序错误类问题。

---

## 一、限制与问题（按严重度排序）

### P1 双路径漂移 —— 最大的结构性风险

门面一旦存在，世界里就有两条装配路径：门面（标准）与手动拼装（进阶/自定义）。
**同一职责多实现**是星期五项目明文记载的最大结构性教训："规则分居两处必漂移，漂移不报错、只出错"。
具体漂移形态：门面里悄悄加了一步初始化（比如某次修复给 Registry 补了默认注册），手动路径不知道 →
两路径产出的对象图行为不一致，测试只覆盖其一，问题静默。

**对策（见 §二 S1）**：门面**只能调用公开 API 组装**，自己不藏任何私有装配逻辑——
手动路径是门面路径的"展开式"，漂移在能力上不可能。但这条纪律本身要靠检查器或评审兜住，又是一笔长期成本。

### P2 默认值即政策 —— 门面会把政策选择静默化

门面必须带默认值才能"一行起动"，而这里的默认值全是**政策**：

- **权限**：现成的 `Permissions.defaultAll(registry)` 给所有组 `"*"` 全权限。门面若默认它，
  宿主在没想过权限的情况下拿到全开权限——对决策内核这类"门禁/编排"组件是危险默认；
  反之若门面默认收紧或必选权限参数，起动成本回升，"一行起动"不成立。
- **压缩器**：`Rollup` 构造强制要 `Compressor` 且实现里直接 `compressor.compress(...)`（**无空保护**）。
  压缩由 LLM 做、宿主注入——门面三个选择都不理想：必选（起动门槛）/ 默认无操作（记忆永远不压缩，
  静默功能缺失）/ 默认抛异常（行为不可预期）。每个选择都是一条要写进红线的政策。
- **会话预算**：`Budget.unlimited()` vs 有限预算——默认无上限会让宿主忘了收束存在。
- **存储根路径**：`Ids.at(root)` 的 root 由谁定、建目录语义（`mkdirs` 稀疏建）默认怎样。

**规律**：门面每内嵌一个默认值，就多一处"没写=继承了某个立场"的静默面。
工具配置层已有"没写=默认静默"的三语义，门面默认值与其叠加后，新人面对的是**两层静默**。

### P3 API 冻结压力与签名演化

- 星期五的先例：`Core.create(config)` 门面已进冻结 API，且膨胀到 **1,294 行 / 70 个公开方法**——
  门面天然吸纳能力（"顺便挂上去"），是**吞噬倾向**的实证。雪豹门面若不设边界，同一路径会重演。
- 门面签名一旦被大量宿主调用，就成了事实契约：新增可选装配项只能靠 overload 爆炸、
  builder（builder 本身又是一套要文档化的 API）或 `CORE_API` 升号（对 provider 的门禁已有，
  对宿主却没有版本门——宿主兼容性无处声明）。
- `Version.CORE_API` 目前只 gate provider；门面演化需要另一套纪律（additive-only），文档与检查器都要跟。

### P4 所有权、生命周期与 god object 退化

- 门面返回什么？若返回聚合一切的 context，就有 **service locator** 退化风险：
  组件不显式收依赖而从门面里摸，测试性与可读性回到"隐式全局"（与星期五"禁 static 全局状态"同一精神）。
- 现有语义里有明确的**运行期控制点**：`Permissions.reload`（热更新不回溯）、`ProviderLoader.unload`
  （模组卸载）、`Names.unregister`（短名释放）。门面若隐藏组件，宿主管不到 reload/unload；
  若全量暴露 getter，门面就退化成"工厂 + 别名表"，减负有限还多一层间接。
- 谁负责生成 `StartupReport`？门面顺手生成则可观测性变成门面专属（手动路径静默丢报告）；
  留给宿主则又是一步默会知识。

### P5 两级结构若被压平，破坏"ID 家"模型

当前组件天然分两级：

- **root 级（共享）**：`Ids`、`ToolRegistry`、`ProviderLoader`、`Permissions`、`ToolConfig`；
- **caller 级（每模型一份，"ID 文件夹=模型的家"）**：`TodoStore`、`NoteStore`、`MemoryStore`、`RawLog`、
  `Rollup`、`Corrections`、`SessionGate`、`ConfirmGate`。

门面若返回单个大对象，多模型场景（多个 caller）要么被误表达为单调用方，要么被迫每 ID 全套重建
（把 root 级共享也复制了）。**门面形状必须显式表达这两级**（见 S2），否则它把架构信息从类型系统里抹掉，
理解成本不降反升——而"降低理解成本"正是加门面的动机。

### P6 测试面影响（211 条 check 的 setup）

- Check 现在用手动装配 = 事实上锁了手动路径。门面出现后：两路径都要测 → 断言翻倍；
  只测门面 → 手动路径失测、漂移回来（P1）；只测手动 → 门面本身失测。
- 合理解法是"门面 dogfood + 保留一条手动装配场景"，但要为此立检查器惯例。

### P7 知识不消失，只是搬家

门面只消灭**标准路径**的装配知识。宿主一旦要自定义（自管权限文件、自定 Compressor、非常规预算），
仍得理解完整装配链——配方文档（B 项教程里的初始化代码块）**不能因门面存在而删**，否则高级场景只能考古源码。
门面降低的是"第一次接入"的成本，不是"理解系统"的成本；概念层问题（术语密度）它一点不解决。

### P8 与 mod-shell 的边界

后续 NeoForge 壳有自己的生命周期（FML 初始化/事件）。门面若渗入 MC 形状的钩子（init/preInit 之类），
零 MC 约束与"core 是普通 Java 依赖"的定位被侵蚀。门面必须**生命周期无关**，壳包门面、不是门面包壳。
（jdeps 零 MC 检查能兜住类型引用，兜不住**概念耦合**。）

### P9 过度承诺的并发语义

Store 内部是 `synchronized` 粒度。门面若被宣传为"安全入口"，宿主可能推断出不存在的线程安全承诺
（如多 caller 并发、跨组件事务）。边界写不清楚就是新的假成功温床。

## 二、若要做：必须遵守的约束（缺一条就建议不做）

| # | 约束 | 针对 |
|---|---|---|
| S1 | **门面只能调公开 API 组装**，零私有装配逻辑、零特权路径；手动路径=门面的展开式。配套：一条手动装配的检查/示例常绿保活 | P1 |
| S2 | **两级句柄**：root 级入口 + `forCaller(id)` 得到 caller 级句柄（各 Store 的显式访问器），类型系统里看得见"ID 家" | P5/P4 |
| S3 | **默认值显式清单**随门面发布（每个默认一句话立场）；权限政策**必选**或至少要求显式声明 `defaultAll`；`Compressor` 允许缺省但必须显式语义（缺省=不压缩且 StartupReport 提示，而非 NPE 或静默） | P2 |
| S4 | 门面签名 **additive-only** 进冻结清单；拒绝"顺便挂能力"——新能力先进组件，门面只在有装配意义时开口 | P3 |
| S5 | **生命周期无关**：不定义 start/stop 之外的钩子，不感知 MC；reload/unload 等控制点保留在组件层，门面句柄只做转发 | P8/P4 |
| S6 | **双路径文档**：门面=标准路径（教程主线），手动装配=进阶附录（配方保留）；`examples/` 一条走手动装配防失测 | P6/P7 |

## 三、对照方案：不加门面（教程 + 示例承担装配知识）

| 维度 | 加门面（受 S1–S6 约束） | 不加门面（B 项教程 + examples 承担） |
|---|---|---|
| 装配顺序错误 | 编译期消灭 | 靠教程抄对，抄错运行期发现 |
| API 面 | +1 入口 +2 句柄类型，进冻结清单 | 零新增 |
| 漂移风险 | 需 S1 纪律 + 保活检查 | 无（单路径） |
| 默认值政策 | 必须内嵌（S3 清单） | 不存在（宿主自己选） |
| 一次接入成本 | 最低（一行 + forCaller） | 低（抄教程初始化块） |
| 自定义场景 | 同现状 | 同现状 |
| 概念层理解成本 | **不变**（术语表仍是刚需） | **不变** |
| 实施成本 | 0.5–1 天 + 检查器 + 文档双轨 | 并入 B 项（≈0 增量） |

**关键观察**：两方案对**最大头的概念层（P7/术语密度）贡献都是零**——
无论选哪个，A 项概念地图与术语表都是前提。门面只改善结构层，且带着 P1–P5 的新成本。

## 四、结论与建议

1. **倾向"受约束地加"，但不是现在**：先落地 A/C（概念地图 + 文档重排）与 B（教程 + examples），
   让装配配方显性化；门面作为配方的**自然收拢**（S1 保证它是同一份知识的固化，不是新知识）。
   顺序颠倒则门面默认值（P2）会在没有红线文档的情况下被静默继承。
2. **若加，形态收窄为**：工厂 + 两级句柄（S2），不是 god object；权限必选/显式（S3）；
   签名进冻结清单 additive-only（S4）。
3. **若裁决不加**：B 项的初始化代码块升格为"装配配方"正式文档 + 手动装配示例常绿，
   P1/P2/P3 风险整体回避——代价只是第一次接入多抄十行。这是**完全可接受的下界方案**。
4. 待裁决变为二选一：**A. 受 S1–S6 约束的两级门面**（先文档后门面）；**B. 无门面，教程+配方承担**。
   两者都以"概念地图/术语表先行"为前提。
