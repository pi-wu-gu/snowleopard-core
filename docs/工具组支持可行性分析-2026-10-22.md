## 〇、项目定位与硬约束

| 项 | 内容 | 对设计的影响 |
|---|---|---|
| 项目名 | **雪豹决策核心**（Snow Leopard Decision Core） | 与"星期五"平级、独立演进，作为**之后的依赖组件** |
| MC 耦合 | **尽可能不与我的世界耦合**——那是其他工具或模组的任务 | 核心零 MC 依赖；MC 接线全部住在模组壳里 |
| 加载形态 | **需要作为模组加载**（2026-10-22 20:32 补充） | 核心 jar + 模组壳双件套；其他模组的工具组经注册接口自动接入 |
| 子模型 | **不包含子模型（subagent）部分**——可被组合出来，不纳入核心 | 核心只留会话/上下文原语，派生能力由工具组组合实现 |
| 记录规范 | 所有记录尽可能附带时间戳 | 存储格式全部内嵌时间戳字段（见各节） |

**结论先行**：用户草案的七节 + 四个自带工具组，**22 条中 19 条可直接落地，2 条需要改写语义，1 条（重名）已给出推荐方案**。
最大的工程量在**记忆组**（分级压缩 + 双根存储 + LLM 压缩 + 纠错通道），约占全部的 45%；
最先要定的是**工具组 ID 与重名规则**——它决定存储布局、权限文件、搜索索引三者的地基。

## 一、总体架构（模组加载形态下的分件）

```
┌─────────────────────────────────────────────────────┐
│ 雪豹决策核心（本项目）                                  │
│                                                       │
│  core（零 MC 依赖，纯 Java）                            │
│   ├─ agent-loop      主循环 / 轮次 / 预算 / 触发分发     │
│   ├─ tool-registry   工具组注册表 + 搜索 + 权限门        │
│   ├─ storage         ID 文件夹 / 时间戳写入 / 结果分级   │
│   ├─ builtin-groups  会话管理 · 记忆 · 任务清单 · 笔记   │
│   └─ contracts       ToolGroupProvider / ToolBackend / HostServices / Result │
│                                                       │
│  mod-shell（NeoForge 适配层，允许 MC 知识）              │
│   ├─ 生命周期接线（进服/退服/tick）                      │
│   ├─ 模组工具组发现与来源标注                            │
│   └─ 配置文件读写（平台侧）                              │
└─────────────────────────────────────────────────────┘
          ▲ 注册接口（ToolGroupProvider）
          │
   其他模组的工具组（自动接入，标注来源 modid）
```

**关键取舍**：「不与 MC 耦合」与「作为模组加载」并不矛盾——
耦合的是 **mod-shell**，不是 core。判据沿用星期五已验证的三层问法：
① 少了它 `ask()` 能否跑完？② 换宿主要不要改？③ 有没有玩家可见界面？
core 三问全"否/不改"，mod-shell 允许 ②③ 为真。

## 二、工具组支持 · 逐条可行性

### 一、规范

| # | 草案 | 判定 | 分析 |
|---|---|---|---|
| 1 | 工具组或工具带自动注入简介 + 用法详解的统一查询入口 | **可行** | 星期五已有雏形：清单 `summary`/`usage` 自动注入 + `tool_help` 统一入口。差别在草案要求**组级与工具级两条注入通道**——组简介注入上下文（便宜），工具详解按需查（省 token）。这正是星期五项目结论"单轮 92% 预算花在工具介绍上"的解法，方向正确 |
| 2 | 工具组必须带简介，工具可选 | **可行** | 加载期校验：无 `summary` 的组拒绝加载（记 ERROR 级），无 `summary` 的工具允许但查询入口回退显示 `（无简介，用 tool_help <name> 看详解）` |
| 3 | 工具组可选带详解，工具必须 | **可行（语义要改一处）** | "工具必须有详解"与"工具简介可选"组合后，最小工具 = 仅详解。建议把详解定义为 `usage + params schema`（结构化字段），而非一整篇散文——否则"必须"会逼出复制粘贴式的假详解。结构化字段机器可校验（缺 `params` 即拒载），散文不能 |
| 4 | 附带产生的信息按工具分文件夹存放 | **可行** | 即"四、存储 2"的直接推论（§九.3 挂载模型）：`ids/<ID>/tools/<工具全名>/` 或专属挂载点。注意**审计与工具产物分开**：审计是安全记录、不是工具产物，不能被工具的删除波及（星期五的 fail-closed 审计即如此） |

### 二、加载

| # | 草案 | 判定 | 分析 |
|---|---|---|---|
| 1 | 多级文件夹分类，需在简介中说明 | **可行** | 文件夹路径即分类树（`local:combat/melee/`），加载时把路径拼进组简介首行：`[分类: combat/melee]`。**不要求作者手写**——手写必漂移（星期五 `docs` 16.8k 行漂移教训），机器拼装后作者只写人话部分 |
| 2 | 外部工具组存放在指定文件路径 | **可行** | 与星期五 `core.tools_dirs` 同构。约定目录布局后由扫描器装载（见下） |
| 3 | 模组工具组自动接入但标注来源 | **可行** | mod-shell 提供 `ToolGroupProvider` SPI：其他模组实现后由 mod-shell 发现（NeoForge `@EventBusSubscriber` 或显式注册表），注册时强制带 `sourceMod` 字段。core 侧只认"来源字符串"，不知道什么是模组 |
| 4 | **自动处理意外的工具组重名** | **可行（方案见 §2.1）** | 这是草案里唯一点名要方案的条目，单列 |

#### 2.1 重名问题的解决方案（草案二、4）

**问题形态**：`local:combat`（外部目录）与 `mod:战斗模组:combat`（模组提供）同名，
或者两个模组都提供 `combat`。重名不处理的后果是**加载顺序决定语义**——最坏的一种静默错误。

**候选方案对比**：

| 方案 | 机制 | 优点 | 致命伤 |
|---|---|---|---|
| A. 先到先得 | 先加载者占用短名，后者被拒 | 简单 | 加载顺序=语义，同一批模组换个加载顺序行为就变 |
| B. 自动改名 | 后者改名 `combat-2` | 都能加载 | ID 与文件夹绑定（存储要求），改名后产物路径漂移，历史记录找不到家 |
| C. 覆盖 | 后来者覆盖前者 | 模组可"升级"工具组 | 静默替换，审计无痕 |
| **D. 限定名 + 显式消歧（推荐）** | 全名永远唯一，短名可配 | 可预测、可审计 | 多一层解析规则 |

**推荐方案 D 的规则**（按优先级依次应用）：

1. **全名（限定名）是唯一权威标识**：`<来源类型>:<来源ID>:<组名>`
   - 内置：`builtin:core:session`
   - 外部目录：`local:<manifest 声明的稳定 gid>:<组名>`——**路径只是加载位置，不进 ID**
     （路径进 ID 会导致目录一挪、ID 一变、存储失联，与"ID 与文件夹绑定"的稳定性要求冲突；
     2026-10-22 21:07 复盘修正）
   - 模组：`mod:<modid>:<组名>`
   - 存储文件夹、权限条目、审计记录**一律用全名**——重名问题在存储层不存在。
2. **短名解析**：模型与配置里允许用短名 `combat`。
   - 短名全局唯一 → 直接解析；
   - 短名冲突 → **不猜、不改名**，返回错误列出候选全名：
     `「combat」有 2 个来源：local:combat:combat、mod:example:combat，请用全名或在配置里配置别名」`
3. **别名表**（可选、显式）：住**权限文件 `aliases` 字段**（随 ID——短名是这个模型的使用习惯，符合"独立个体"；见 §二.五 示例）。
   别名冲突同样拒绝加载（配置错误记 ERROR）。
4. **同全名重名**（同一模组重复注册 / 目录里两份同名组）：**后者拒绝 + ERROR 记录**，
   不覆盖不改名。理由：同名同源的重复注册是打包错误，静默取任何一份都是掩盖 bug。
5. **每轮启动报告输出一次"重名消歧表"**（哪些短名有歧义、用了什么别名），
   让歧义可见而不是等模型踩。

**为什么不用 B（自动改名）**：草案同时要求"ID 与文件名称绑定、所有工具默认使用对应 ID 的文件夹"——
改名会导致 ID 不稳定，昨天 `combat-2` 今天变 `combat-3`，产物与权限配置全部失联。
**稳定性优先于便利性**，歧义就该被显式暴露。

### 三、搜索

| # | 草案 | 判定 | 分析 |
|---|---|---|---|
| 1 | 按简介/详解关键词检索组或工具 | **可行** | 加载期建倒排索引（分词 = 简单空白/标点切分即可，中文按字符 bigram）。查询入口 `tool_search(query)` 返回命中的组/工具短名 + 简介行。**索引常驻内存**：工具组数量级是几十~几百，全文索引体积可忽略 |
| 2 | 按来源模组分类搜索 | **可行** | 索引的 `sourceMod` 字段过滤，与 1 组合成 `tool_search(query, source="example")`。来源标注（二、3）在此兑现价值 |

**注意**：搜索只搜**简介与详解**，不搜工具运行产物（那是存储层的事，语义完全不同，混在一起会把"工具说明"和"工具输出"搅在一个索引里）。

### 四、存储

| # | 草案 | 判定 | 分析 |
|---|---|---|---|
| 1 | 主文件夹目录下指定文件夹（可设置） | **可行** | `storage.root` 配置项，默认 `<base_dir>/snowleopard/`。**相对路径以 `core.base_dir` 为基准**（星期五踩过"路径基准差一层"） |
| 2 | 单 ID 独立文件夹，ID 与文件名绑定，工具默认用对应 ID 文件夹 | **可行（改一处语义）** | 见下 |

**存储布局建议**（含草案未覆盖的一个缺口）：

```
<storage.root>/
├─ ids/
│  ├─ id0/                       # 默认启动（权限全开）的 ID 文件夹 = 模型的家（§九.1）
│  │  ├─ model-info/             # 自身信息
│  │  ├─ files/                  # 自身文件
│  │  ├─ tools-default.json      # 工具默认配置（§九.2）
│  │  ├─ session/                # 会话管理组的挂载点
│  │  ├─ memory/                 # 记忆组 · 压缩记忆根（独立根 ✓）
│  │  ├─ memory-raw/             # 记忆组 · 轮次原始记录根（独立根 ✓，与上互不嵌套）
│  │  ├─ todo/                   # 任务清单挂载点
│  │  ├─ notes/                  # 笔记挂载点
│  │  ├─ tools/<工具全名>/       # 其余工具的默认工作目录（§九.3）
│  │  └─ audit/                  # 审计（见下）
│  └─ <其他ID>/                  # 同构，**互相隔离**（§九.3）
├─ tool-configs/                 # 工具配置文件：可多个，启动时引用（§九.2）
└─ groups/                       # 工具组定义（跨 ID 共享）；别名随 ID 住权限文件
```

**缺口：审计的归属**。草案说"附带产生的信息按工具分文件夹"，但**审计不是工具产物**——
它是"谁在什么时候做了什么"的证据（21:38 后无审批概念，含模型自确认动作）。建议：`audit/` 与工具产物平级、**工具不可写不可删**，
只由核心追加。否则一个有 `file_delete` 能力的工具组可以抹掉自己的操作审计。

### 五、权限

| # | 草案 | 判定 | 分析 |
|---|---|---|---|
| 1 | 默认启动（全权限，ID0）/ 指定 ID 启动（权限配置，输入优先于自带；未启用工具仅可见名称不加载简介；失败记 "XXX配置失败"） | **可行** | 与星期五 `ToolState` + 配置优先级 CLI>ENV>文件>默认同构。**注意 `NEEDS_APPROVAL` 不迁移**——雪豹无审批概念（21:38），只有 开/关 + `availability` 三档。**"未启用工具仅可见名称"很关键**——它正是"省 token"与"知道它存在"的平衡点：注入一行名字，不注入简介/详解（详解在被启用前不可查，否则禁用形同虚设） |
| 2 | 可热更新 | **可行（加一条约束）** | 配置文件变更 → 重建权限表 → **只影响之后的调用**。已在执行中的调用不回溯（否则半路被撤权的工具会产出"执行了一半"的状态）。变更事件写审计 |
| 3 | 不可禁用 / 常规 / 默认禁用 三档 | **可行** | 清单字段 `availability: ALWAYS_ON | NORMAL | DEFAULT_OFF`。`ALWAYS_ON` 的工具组（会话管理、记忆）在权限文件里被写"禁用"时**配置失败并记警告**——不允许配置把核心能力关掉（草案的"！！！不可禁用！！！"语义） |

**权限文件形态建议**（三级，与"ID 与文件名绑定"对齐）：

```json
{
  "id": "id3",
  "extends": ["id0"],                      // 可选继承
  "groups": {
    "builtin:core:memory":   { "tools": "*" },
    "mod:example:combat":    { "tools": { "attack": "enabled", "nuke": "disabled" } },
    "local:notes:notes":     { "tools": "*" }
  },
  "aliases": { "战斗": "mod:example:combat" }
}
```

- **输入的配置文件优先于自带**（草案原文）：启动参数 `--perm <file>` 覆盖 `groups/` 下的自带文件；
- 加载失败的具体工具记 `「<全名>:<工具名>」配置失败：原因`，**部分失败不整体拒绝**（一组坏了不该锁死全部），但 ID 的 `配置失败` 计数进启动报告。

### 六、结果

| # | 草案 | 判定 | 分析 |
|---|---|---|---|
| 1 | 成功/警告/严重警告/错误 四级（正常 / 有影响不严重 / 有影响很严重但能运作 / 显而易见） | **可行** | 定义 `ResultLevel { OK, WARN, SEVERE, ERROR }`。映射到模型可见语义：OK=照常返回数据；WARN=返回数据 + `⚠` 描述；SEVERE=返回**部分数据** + `⚠⚠` 描述（仍能运作是硬要求——SEVERE 不是 ERROR 的别名，它是"带伤运行"）；ERROR=无数据、只有失败原因 |
| 2 | 除成功外均带描述字符串 | **可行** | 构造期强制：`Result.warn("...")` 无描述直接抛——把规范变成 API 形状，而不是靠人记得写。**星期五的反面教材**：工具失败曾返回 `"[failed]"` 文本被包成成功（假成功家族），所以这次四级要在**返回值类型**上分家，不靠字符串约定 |

### 七、触发

| # | 草案 | 判定 | 分析 |
|---|---|---|---|
| 1 | 主动唤起 / 每次会话开始/结束 / 每轮开始/结束 | **可行** | 触发点四类全部落在主循环上：`onSessionStart/End`、`onTurnStart/End`（轮 = 一次模型请求的完整往返）。工具组在清单里声明 `triggers: ["turn_end"]`，注册进分发表 |
| 2 | 主动唤起必须有回应，被动触发可选 | **可行（建议收紧一处）** | 主动 = 工具调用，必须返回 `Result`（天然有回应）。被动触发建议**默认必须返回、可显式声明 silent**——完全可选会导致触发器静默吞错。触发器异常按分级记录并继续（内置 WARN/ERROR、模组可 SEVERE——不能让一个组的坏钩子杀掉整轮） |

**触发的顺序语义要写死**：同一触发点多个组响应时，按 `组全名的确定序` 依次执行（字典序），
声明 `priority` 可调。不写死顺序 = 重名问题的翻版（这次是执行序）。

## 三、自带工具组 · 逐条可行性

### 一、会话管理（不可禁用）

| # | 草案 | 判定 | 分析 |
|---|---|---|---|
| 1 | 结束本轮会话，不触发下一次发送 | **可行** | `session_yield` 工具：模型主动收束本轮。实现为主循环的"提前正常结束"信号（区别于轮次上限耗尽）。星期五的 `AgentLoop` 已有预算出口机制，同构 |
| 2 | 可配置的轮次、消耗上限 | **可行** | 即星期五 `SessionBudget`（轮次/token 双预算）。超限 = 强制收束，按 SEVERE 返回"预算耗尽"并自动注入摘要 |
| 3 | 自动注入：当轮总消耗、上句消耗、余量、轮次消耗 | **可行** | 上下文装配器的固定尾注段。四个数字都从 LLM 响应的 usage 累计得来。注意"余量"要有口径：`余量 = 上限 - 累计消耗`，上限未配置时显示"无上限"而不是 0（星期五 `ConfigPanel` 显示 0 的 bug 教训） |

### 二、记忆（不可禁用）——工程量最大的一组

> **稀疏性硬约束（2026-10-22 21:28 用户指出）**：**原始记忆必须调用过才产生**——
> 某天没有任何对话轮次，那一天就**没有原始记录、也没有任何压缩档**，这是**正常状态**而非缺口。
> 全组的压缩、补做、完整性修复、默认加载都必须以"**有原始记录才算存在**"为第一判据：
> **空档永远不补、不报缺口、不参与"紧邻"取值**。
>
> **推论：周期翻转的压缩是惰性的**。判断点挂在"每轮结束检测"上（草案原文），无调用日没有触发时机——
> 跨过一个空周末/空月末，该做的天/周归档**推迟到下一次轮末检测或启动 catchup 时补做**。
> 不需要墙钟定时器：没有调用就没有新记录，定时器只会对着空档空转。
> 惰性推迟不等于丢失——"该周期有记录但翻转后还没归档"正是 catchup 与完整性修复的正常目标。

### 4.1 双件套结构

| 件 | 内容 | MC 知识 |
|---|---|---|
| `snowleopard-core` | 主循环 / 注册表 / 存储 / 内置工具组 / 全部契约接口 | **零**（纯 Java 21，单 jar） |

### 4.2 其他模组的工具组如何自动接入（草案二、3）

```java
// core 侧（零 MC 依赖）的注册契约
public interface ToolGroupProvider {
    ToolGroupDescriptor describe();      // 组名/简介/详解/分类/触发声明/可用性三档
    ToolBackend backend();               // 工具实现
}
```

mod-shell 侧的发现顺序（启动一次）：

1. **内置组**：`builtin:core:*`（会话/记忆/任务/笔记）；
2. **外部目录**：`storage.groups_dir` 下的 `*.group.json` + 实现 jar → `local:*`；
3. **模组提供**：NeoForge 的服务发现（`ServiceLoader` on mod classpath）或
   事件总线注册（`ToolGroupRegisterEvent`）→ `mod:<modid>:*`，**强制标注来源 modid**。

每条注册记录进启动报告：`工具组 12 个（内置 4 · 外部 5 · 模组 3 [jei, create, example]）`，
并按 §2.1 做重名消歧。

### 4.3 模组加载特有的三个风险

| 风险 | 分析 | 对策 |
|---|---|---|
| **类加载隔离** | 模组 A 的工具组引用 A 的类，core 反射加载会 NoClassDefFoundError | 工具实例由**提供方自己的类加载器**创建（Provider 模式天然满足），core 只持有接口引用 |
| **模组热重载/卸载** | 模组被卸载后其工具组仍挂在注册表 → 调用即炸 | `mod-shell` 监听模组卸载 → 注销其组并记 WARN；已在执行的调用允许完成（不回溯） |
| **版本漂移** | 模组重编译后 `ToolGroupDescriptor` 契约不匹配 | `core_api` 版本号（星期五 `core_api: 1` 的做法），不匹配拒载 + ERROR |

### 4.4 模组侧"自带工具组"的边界

草案的四个自带组**全部住 core**（它们是"决策核心"的一部分，与 MC 无关）。
MC 相关的能力（界面操控、移动、挖掘……）属于其他模组经 `ToolGroupProvider` 接入的
工具组——这正是"不与我的世界耦合，那是其他工具或模组的任务"的落点。

## 八、待决策四项的决议（2026-10-22 20:57 (UTC+8)）

### 8.1 次路由 = **单次思考及调用**

记忆组 6 的"次路由"粒度定为：轮内的**每一次思考**与**每一次工具调用**都是一个可路由条目，
各自带序号。`memory_read(level="轮", period=<轮>, sub=<条目号>)` 可定位到"第 n 次思考"或"第 n 次调用"。

**推论（原始记录的行结构由此定死）**：轮原始记录必须是**结构化条目流**而不是纯文本——
每条至少含 `{seq, ts, kind: thought|tool_call, payload}`。`kind=tool_call` 的条目
**不含工具完整输出**（草案二、2）但含调用名与时间戳；`seq` 即次路由的地址。

### 8.2 记忆默认加载 = 未完成压缩的部分 + 其之前完成压缩的一级 + 年记忆完整加载

草案二、5"默认分级加载最后一级压缩记忆"的口径定为**三层**（**稀疏感知**：每层只取"存在的"，空档跳过）：

| 层 | 内容 | 例子（周三加载时） |
|---|---|---|
| 年记忆 | **完整加载**（不是摘要的摘要） | 2026 年档全文 |
| 紧邻的已完成压缩 | **未压缩部分之前最近一个"存在的"已完成档**（21:22 裁决：周期翻转时取"周日"；**若周日没调用就往前找**，绝不放一个空占位） | 昨天的日压缩；周一 00:05 则取**周日**的日压缩（周日空 → 取周六、周五……第一个有档的） |
| 未完成压缩的部分 | **所有未压缩的周/月/日/年**（21:22 裁决；**只列有原始记录的**） | 本周暂存 + 本月未压缩尾部 + 今天未压缩 + 今年未压缩尾部（哪层没调用就哪层不出现在注入里） |

这与原建议（"最近完结周期 + 当前暂存"）一致，但补上关键一条：**年记忆必须完整**——
它是长期背景，不允许再截断。代价可控：年档本身已是压缩产物；若年档超长，
提供 `memory.year_max_chars`（**默认不限**，尊重草案二、4"默认不设上限"）。

**注入行不为空洞辩护**：某层没有内容就不注入那一行，而不是注入"（当日无记录）"占位——
占位会让模型以为"有东西没看到"。只有**纠错条目**（§三.二.8）例外：它跟着目标记忆走，
目标记忆不存在时纠错条目挂起并记 WARN（孤儿纠错条目本身是完整性问题）。

### 8.3 删除语义：按建议通过

笔记删除 = 回收站（`notes/.trash/<ts>/`）· 任务子条目删除 = 标记不删（真删走显式 `purge`）·
记忆纠错移除 = 真删但留审计。三者不一致是故意的（风险不同）。
**凡需二次确认处，确认都是发给模型自身的**（21:38 更正：是确认不是审批）——两段式调用 + `confirm_token`。

### 8.4 SEVERE 不强加给系统自带工具

四级结果 API（§二.六）**仍然实现**——那是模组工具需要的功能（"有影响且很严重但仍能运作"
多见于世界类工具）。用户原话是"**如果不需要不用强加**"：内置组**不要求凑齐四级**，以 OK/WARN/ERROR 为主；
但**语义确为"带伤运行"时允许 SEVERE**——本分析仅两处：会话预算耗尽的强制收束（§三.一.2）、
`memory_repair` 修复后仍有残留缺口（§三.二.9）。**不为凑数制造 SEVERE**。
触发器同理：内置触发器 WARN/ERROR，模组触发器可 SEVERE。

## 九、ID 文件夹与工具配置模型（2026-10-22 20:57–20:59 (UTC+8) 用户追加）

### 9.1 ID 文件夹即"模型的家"

`ids/<ID>/` 不再只是权限桶，而是该模型实例的完整工作区：

```
ids/<ID>/
├─ model-info/            # 自身信息（身份、偏好、状态）
├─ files/                 # 自身文件
├─ tools-default.json     # 工具默认配置（无外部设置时用它）
├─ <各工具挂载点>/        # 见 9.3
└─ audit/                 # 审计（工具不可写删）
```

ID0 = 默认启动（完全工具访问权限）的家。"模型信息按 ID 文件夹存储"意味着
**模型的可变状态全部随 ID 走**——换 ID 启动即换一套完整隔离的家，不需要额外的状态迁移逻辑。

### 9.2 工具配置文件：两级来源、单文件全覆盖、三种语义

**两级来源**（优先级从低到高）：

| 级 | 位置 | 用它 when |
|---|---|---|
| ① 自带默认 | `ids/<ID>/tools-default.json` | 无外部设置（"无外部设置即使用其自身默认设置"） |
| ② 外部配置 | `tool-configs/` 下可多个，**启动时引用**（如 `--tool-config work.json`） | 被启动参数点名；**覆盖 ①** |

**单文件配置全部工具**：一个配置文件覆盖整张工具表（组/工具的参数与行为选项；**开关归权限文件**），
**没写到的工具 = 默认设置**（不报错、不视为遗漏——这是"单文件全覆盖"的正确语义）。

**三种语义**（草案原文，映射到结果分级 §二.六）：

| 情形 | 判定 | 级别 | 说明 |
|---|---|---|---|
| 没写某个工具 | 用默认设置 | OK | 静默，不产生记录 |
| **匹配失败**（配置里写了不存在的组/工具名） | 继续启动 | **WARN** + 描述 | 合理场景：配置跨档共用、模组未装。警告内容含"配置项 X 没有匹配到任何工具" |
| **参数错误**（工具存在但值不合法/类型错/越界） | 该项配置拒绝生效 | **ERROR** + 描述 | 不允许"半生效"——错误值宁可退回默认并大声报错 |

**与权限配置的关系**（两者职责不同，**不合并**）：

- 权限配置（§二.五）管"能不能用"：未启用工具仅可见名称、不加载简介；
- 工具配置（本节）管"怎么用"：参数默认值、行为选项。
- 重叠部分（工具开关）以**权限文件为准**——安全判定单点收口，避免两处打架
  （星期五的教训：同一职责分居两处必然漂移）。

**ID 自带默认文件里的匹配失败也按 WARN 处理**：模型换了一套工具（模组增删）后，
家里的旧配置出现失效项是常态，不该让模型的家"坏了"。

### 9.3 工作目录挂载：默认挂 ID、互相隔离

**规则**：所有工具工作时的文件夹**默认挂在调用它的对应 ID 模型文件夹中**（`ids/<ID>/<挂载点>/`），
不同 ID 之间**互相隔离**。

| 含义 | 影响 |
|---|---|
| "默认" = **唯一规则**：挂载一律锚定 `ids/<ID>/`，**不提供跨 ID 挂载通道** | 工具 = 功能复用，**不复用信息** |
| "调用它的对应 ID" = 按**会话所属 ID** 解析，不是按工具来源 | 模组工具调用同样落进调用者的 ID 家 |
| "互相隔离" = ID 之间不可见、**不可读**、不可写对方挂载点（**含只读**） | ID3 的笔记工具看不到 ID0 的 `notes/` |

> **裁决（2026-10-22 21:07）**：跨 ID 访问（含只读引用）**一律禁止**——允许会导致不同 AI 互相可读取文件，
> 不符合设计目标。调用按 ID 分隔**独立个体**；工具仅仅是功能复用，不复用信息。

**三个推论**：

1. **并发安全**：两个 ID 同时跑同一工具，各写各的家，天然无竞争；
   同一 ID 内的并发走**资源锁**（工具清单 `resource_locks` 声明，继承星期五机制，按 `caller_id:锁名` 作用域化）。
2. **审计按 ID 落**：`ids/<ID>/audit/`，工具不可写删（§二.四 结论不变）。
3. **记忆组的双根**在挂载模型下保持独立顶层：`ids/<ID>/memory/` 与 `ids/<ID>/memory-raw/`
   互不嵌套、删一不影响二（草案二、2"不共用根"仍成立）。

~~新开的唯一小口径：跨 ID 只读引用~~ → **已裁决（21:07）：一律禁止**，连白名单也不留。
任何"跨 ID 看一眼"的通道都会破坏"独立个体"这个设计目标——AI 之间要交换信息，
走**显式输出/输入**（用户搬运），不走工具读取。

### 9.4 布局定稿（替换 §二.四 的草案）

见 §二.四 的更新版布局图（`ids/<ID>/` = 家 + 挂载点 + `tools-default.json`；
`tool-configs/` = 外部配置库；`groups/` = 工具组定义共享）。

### 9.5 风险与边界

| 风险 | 对策 |
|---|---|
| 配置文件"匹配失败"被忽略成常态（WARN 刷屏后没人看） | WARN 汇总进启动报告"配置失效 N 项"，连续启动都失效的项升级提示清理 |
| `tools-default.json` 与外部配置同时改同一键 | 优先级表（9.2）写进启动报告"生效配置来源：external/id-default/内置默认" |
| 工具被配置成把挂载点指到自己的 ID 之外 | 路径解析**强制锚定** `ids/<调用方ID>/` 前缀（越界即 ERROR）；**不存在**跨 ID 或全局挂载通道（21:07 裁决） |
| 工具需要共享的只读参考数据（配方表等） | 随**工具组包**分发、只读、不进任何 ID 家——那是"功能资产"不是"模型信息" |

### 9.6 调用方 ID 随调用默认传输（2026-10-22 21:07 用户追加）

> 「追加调用工具时默认传输调用方 ID 以服务于工具分辨模型数据源。」

**规则**：每次工具调用，核心在调用上下文里**默认携带调用方 ID**（`caller_id`），
工具据此分辨"我在为哪个模型服务"，从而把数据源解析到 `ids/<caller_id>/`。

| 设计点 | 决定 | 理由 |
|---|---|---|
| 传输通道 | **调用上下文字段**（core 注入），不是工具参数 | 工具参数是模型可见/可填的——让模型填 ID 就等于把钥匙交给被隔离者 |
| 工具侧可见性 | 工具组实现**只见 `caller_id` 字符串**，无路径拼接权 | core 统一解析路径，工具拿不到 `ids/` 根，从能力上杜绝越界 |
| 模组工具 | 同样默认携带；不关心可忽略 | "分辨模型数据源"是服务，不是义务 |
| 审计 | 每条审计记录**含 `caller_id`** | 出事后能回答"是哪个 ID 的模型干的"（星期五 Actor 机制同理：核心设置、模型无法伪造） |

**与 9.3 的关系**：9.3 是"文件放哪"（挂载隔离），9.6 是"怎么知道是给谁放的"（数据源识别）。
两者合起来才是完整闭环：**调用 → 携带 caller_id → core 解析到该 ID 的挂载点 → 工具在沙箱内读写**。

**防伪要点**（星期五教训"Actor 由核心设置、模型无法伪造"的移植）：
`caller_id` 只由核心的会话归属注入，**不接受任何来自模型侧的覆盖**；
工具若声明"可自定义数据源"参数，core 在装载期拒绝该清单（配置错误级）。
