# 开发者理解成本分析 —— 如何减轻其他开发者的理解难度

> 前提阅读：`README.md`、`docs/工具组支持可行性分析-2026-10-22.md`、`docs/开发流程-2026-10-22.md`
> 本文是分析与建议，**不含改动**——待裁决后按优先级实施。

## 〇、两类读者，两条路径

"其他开发者"不是一种人，减负手段必须分轨：

| 读者 | 要做的事 | 现在靠什么学会 |
|---|---|---|
| **接入者**（外部模组作者） | 实现 `ToolGroupProvider`、装载、返回 `Result` | javadoc + 599 行可行性分析（无教程、无示例） |
| **贡献者**（改 core 本身的人） | 改行为、加工具组、跑 check、保持纪律 | 9 个 Check 的文件头注释 + 开发流程 + 对话史料 |

两条路径的文档需求不同，混在一份 README 里互相拖累。以下措施全部标注服务哪类读者。

## 一、现状盘点（事实）

| 项 | 事实 | 理解影响 |
|---|---|---|
| 产品代码 | 3,768 行 / 23 类，最大文件 328 行 | **规模不是负担**——成本在概念密度 |
| javadoc | 每类 19–29 行，含"为什么"，多处引用 `§四/§二.2.3` | 质量高，但章节号引用**要求读者手边摊着那份 599 行文档** |
| README | 48 行：AI 声明 + 定位表 + 构建 + 里程碑表 | 是**项目档案**，不是上手指南；无 quick start、无 API 导览 |
| docs/ | 仅 2 份带日期的长文（可行性 599 行 + 流程 211 行） | 是**设计史料**而非使用文档；没有阅读路径，新人不知从哪进 |
| examples/ | **不存在** | 接入者无"最短闭环"可抄 |
| package-info.java | **不存在** | 包分层职责只存在于开发流程文档中 |
| 装配入口 | **无门面**——宿主自己拼 `Ids.at → ToolRegistry → ProviderLoader → Permissions → 各 Store` | 装配顺序只隐含在 9 个 Check 的 setup 里，属于**默会知识** |
| 行为规格真相 | 211 条 check（9 类） | 锁得很牢，但 check 是测试代码，不被当作规格来读 |
| 自造术语 | 限定名 / 短名歧义 / 次路由 / SEVERE 带伤运行 / 两级配置三语义 / 稀疏记忆 / 平级五层 / 惰性压缩 / 冷却补做 / 完整性修复 / confirm_token / caller_id / ID 家…… | **概念密度是最大头**——每个词都要一次性的上下文才能解码 |
| AI 产出声明 | README 首屏明示"几乎完全由 AI 完成" | 诚实且必要；副作用：设计理由散在对话里，**人类接手者更需要显性化**的决策记录 |

## 二、理解难度的四个来源（按大小排序）

1. **概念层（最大）**：十几个自造术语没有一处集中定义；术语与类的对应关系（"次路由"→ `RawLog.readEntry`）要靠读代码反推。
2. **结构层**：没有装配门面、没有 examples——"Hello World 接入"要自己从 Check 的 setup 里考古。
3. **文档层**：README=档案、docs/=史料，缺一份"先读什么"；规范要点被摊在 599 行里，javadoc 用章节号回指它，形成阅读死锁（要懂 javadoc 先读完 599 行，要读 599 行先懂 javadoc）。
4. **API 层（最小但刺眼）**：个别签名削弱理解——`Names.resolve` 返回 `Object`（实为 `Qualified | Ambiguous | null`），读者必须读实现才知道有哪几种情形；包级职责无 `package-info`；冻结契约无 `@apiNote` 标注。

## 三、减负措施（按杠杆排序）

### A. 一页「概念地图 + 术语表」（服务两类读者 · 杠杆最高 · 成本半天）

新建 `docs/概念地图-2026-10-23.md`（或并入 README 顶部）：

1. **生命周期图**（一图）：外部调用的完整链路
   `ToolGroupProvider.describe() → ProviderLoader.load → Names 拼限定名 → ToolRegistry 注册 → Permissions 门禁 → Ids 家定位 → 执行 → Result 四级返回 → StartupReport`。
2. **术语表**（每词三行以内）：词条 · 一句话定义 · 对应类/方法。例：
   - **限定名** `<类型>:<来源ID>:<组名>` —— 全局唯一工具组标识，由装载器拼、provider 不构造（防冒名）。→ `Names.Qualified`
   - **稀疏记忆** —— 原始记录必须调用过才产生；无调用日=不存在，空档不补、不参与"紧邻"取值。→ `MemoryStore.loadDefault`
   - **带伤运行**（SEVERE）—— 部分数据+描述，仍能运作；只用于预算收束与修复残留两处。→ `Result.Severe`
3. 每条术语给**英文对照**（qualified name / sparsity / lazy rollup），便于检索与非中文读者。

**为什么有效**：概念解码从"考古式"变成"查表式"；这张表同时是 README 的首屏摘要。
**风险**：低。唯一纪律是术语表与代码漂移——把术语表纳入 `DocsCheck` 白名单即可（本仓已有该机制，新使用类文档要登记）。

### B. 30 分钟接入教程 + `examples/` 最小闭环（服务接入者 · 杠杆高 · 成本 1 天）

1. `docs/接入指南-2026-10-23.md`：从零到一次调用的分步教程，按"复制粘贴即可跑"标准写：
   - 步骤 1 继承 `ToolGroupProvider.Simple` 写一个回声工具组；
   - 步骤 2 按固定顺序装配（给出**完整初始化代码块**）；
   - 步骤 3 装载并读 `StartupReport` 的 WARN 汇总；
   - 步骤 4 调用一次工具，读懂 `Ok/Warn/Severe/Error`。
2. `examples/hello-provider/`：与教程对应的可编译源码 + `README` 两行运行命令。
3. 教程正文中嵌「**接入红线**」小节（见 C.3）。

**为什么有效**：装配顺序从 Check 的默会知识变成显式配方；示例即规格的最短投影。
**风险**：示例会漂移——把它挂进 `build.sh check`（编译 examples 即断言），比文档检查更硬。

### C. 文档重排（服务两类读者 · 成本 1 天）

1. **`docs/INDEX.md` 文档地图**，三栏分类并给出阅读顺序：
   - *上手*：接入指南、概念地图、examples；
   - *参考*：javadoc、行为规格清单、manifest JSON 形态（现藏在 `loadManifest` javadoc 里，值得外提一页）；
   - *史料*（只答"为什么"）：可行性分析、开发流程——标注"新人不必通读"。
2. **README 瘦身**：保留 AI 声明/定位/构建；里程碑表移入开发流程；首屏改为概念地图摘要 + 三条阅读路径（接入者/贡献者/只想跑起来）。
3. **《接入红线》一页**（可并入接入指南）：六条硬规则 + 违反后果 + 兜底检查器在哪：
   非 OK 必须带描述（构造期抛）｜ provider 不构造限定名（装载器拼）｜ 跨 ID 一律禁止 ｜ 失败必须抛异常不许返回文本 ｜ `coreApi` 不匹配即拒载 ｜ `caller_id` 不可伪造（core 注入）。

**为什么有效**：切断"javadoc 章节号 ↔ 599 行"的阅读死锁；史料与规范分流（星期五项目 56 份历史文档与 `DocsCheck` 白名单的教训——**第一天就分轨，别等事后再切**）。

### D. API 形状小修（服务接入者 · 成本 1–2 天含全量 check）

1. `Names.resolve` 的 `Object` 返回改为 sealed 查询结果（`Resolved | Ambiguous | NotFound`）——这是"形状即文档"的既有哲学（`Result` 已经这么做）的自然延伸；
2. 每包加 `package-info.java` 一段话（契约/装配/能力/基础四层职责各一句）；
3. 冻结契约标 `@apiNote`/`@implNote`（`ToolGroupProvider`、`Result`、`Version.CORE_API`、`Ids.Caller`）；
4. javadoc 内 `§四/§二.2.3` 式引用改为「文档名+章节标题」，或直接内联一句要点。

**为什么有效**：读者不必读实现就知道全部分支；包结构自解释。
**风险**：改签名牵动 211 条 check 中的既有断言，须按铁律全仓 grep 旧用法后一次改净。**这是唯一的代码变更项，建议单独一轮做完并整体回归**。

### E. check 即规格的可读化（服务贡献者 · 成本半天）

导出 `docs/行为规格清单-2026-10-23.md`：9 个 Check 类 × 各自锁定的契约句（文件头注释已是现成素材，如 SmokeCheck 锁"工程骨架意图"）。README 链接之。惯例补充：**每个 Check 文件头必须写"本文件锁什么契约"**——现有文件已达标，新文件照办。

### F. 术语命名对冲（服务两类读者 · 成本半小时）

中文概念保留中文（对目标读者友好），但所有自造词在术语表给英文对照；"SEVERE/带伤运行"这类双语概念在 javadoc 里显式绑定，检索任一语言都能命中。

## 四、优先级与分工建议

| 顺序 | 项 | 成本 | 服务 | 备注 |
|---|---|---|---|---|
| 1 | A 概念地图+术语表 | 半天 | 两类 | 即刻见效，零风险 |
| 2 | C 文档重排 + 接入红线 | 1 天 | 两类 | 与 A 同轮做，DocsCheck 登记新白名单 |
| 3 | B 接入教程 + examples | 1 天 | 接入者 | examples 挂 build 检查防漂移 |
| 4 | E 行为规格清单 | 半天 | 贡献者 | 素材现成 |
| 5 | D API 小修 | 1–2 天 | 接入者 | **单独一轮 + 全量回归**；改 `resolve` 签名须全仓 grep |

合计约 4–5 个工作日（均为文档/示例级改动，仅 D 动代码）。

**明确不建议做的**：
- 大规模重命名或重写代码——3,768 行规模可控、javadoc 质量已高，重写风险大于收益；
- 画大型 UML 全景图——一页概念生命周期图已够，全景图维护成本高且必过期；
- 给史料（可行性分析/开发流程）做"改写成教程"——史料的价值就是当时事实（星期五 `DocsCheck` 误判教训），教程另写，别动史料。

## 五、从星期五项目直接迁移的三条经验

1. **使用类文档与史料第一天就分轨**（星期五 56 份历史文档迫使 `DocsCheck` 用 8 份白名单豁免——事后再切很痛）；
2. **完整性靠机制不靠人记**（`RuleApprover` 整类缺失的教训）——examples 编译检查、术语表进 DocsCheck 白名单，都按此设计；
3. **追加式写文档必造自相矛盾**——概念地图/术语表采用"整篇重写"维护法，不逐轮追加。
