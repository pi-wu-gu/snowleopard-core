## 〇、先厘清：影响力排序 ≠ 实施顺序

理解成本分析 §四的表是按**影响力**排的（A > C > B > E > D）。实施必须按**依赖**排，两者不同：

- C（INDEX/README 收口）的职责是"编目"——**A/B/E 的产物先存在，INDEX 才有东西可编目**；
- B（教程）要嵌入红线、引用术语表——**A 与红线先行**；
- D（API 小修）改变签名——**任何"教 API 形状"的文档写在 D 前都会返工**。

故实施序调整为 **A → B+E → C → D → 分叉收尾**；影响力不变，只是把 C 从第 2 挪到第 3。

## 一、机械事实（决定顺序的硬约束，全部已核对代码）

| # | 事实 | 后果 |
|---|---|---|
| M1 | `DocsCheck` **按固定路径点名** README + 两份设计文档，不扫其他文件 | 新增文档（概念地图/接入指南/INDEX/红线/规格清单）默认**漏检**——每份新使用类文档都要**同步扩展 DocsCheck**（星期五教训的镜像：那边是白名单 8 份防误判，这边是点名 3 份防漏检） |

| M3 | DocsCheck 规则 3：README 反引号里的 `XxxYyy` 类名必须真实存在于 src | README/新文档**不得反引号引用尚不存在的类**（如未来的 `bootstrap` 门面类）——波次 5 才允许 |

| M5 | `build.sh check [name]` 按 `XxxCheck` 命名派发，`check all` 秒级全绿 | examples 防漂移 = 新增/扩展一个 Check 即可挂进全绿门；每波结束跑 `check all` 成本≈零 |
| M6 | DocsCheck 规则 5：`confirm_token / session_yield / memory_repair / purge` 两文都有 | 新术语表**应收录这四个机制键**（扩展判据时顺手对齐），防"一处改了另一处没跟" |

## 四、关键路径与并行度

- **关键路径**：0 → 1 → 2 → 3 → 4 → 5。文档链（1→2→3）不可颠倒的理由：红线嵌教程、INDEX 编目全员。
- **可并行**：E ∥ 1/2（素材=9 个 Check 文件头，零依赖）；D 的 package-info/@apiNote 部分 ∥ 2/3（不动签名零风险）。
- **建议不并行**：D 与 B/C 文档定稿——即使教程已避开 resolve，STALE 清扫和 §引用改写会碰同一批文档文件，并行必互相踩。
- **波次 0 的真实作用**：只分叉波次 5。若用户久不裁决，1–4 照走，**唯一后果**是 C 的"标准入口"栏留待补半日适配（成本已计入 5A/5B）。
